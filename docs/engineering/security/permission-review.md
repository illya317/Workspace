# 权限定期复查与异常通报

## 目标

权限复查不是根据岗位名称猜测谁“看起来应该有权”，而是把已审核的系统结构和全部显式授权事实保存为租户核准基线，再用同一引擎检查授权变更后的即时状态与每日全量状态。

权威配置位于 `WORKSPACE_CONFIG_DIR/config/tenant/permission-review.json`。它必须和应用代码分开维护，但随租户配置 manifest 一起校验、备份和部署。

## 执行策略

| 触发 | 时间 | 范围 | 目的 |
|---|---|---|---|
| 即时复查 | 每次后台授权事务提交后 | 当前完整权限状态 | 授权或撤销造成异常时立即强提醒 |
| 每日复查 | 租户业务时区每日 08:00 | 完整资源、授权、组织和职责分离状态 | 兜底发现导入、组织调岗、模块变更或非标准写入造成的漂移 |
| 人工只读复查 | `npm run permission-review:check` | 同每日复查 | 上线前或调整基线前查看异常，不写状态、不发通知 |

Next Node 运行时在启动时注册每日调度。多实例或候选进程偶遇同一执行时刻时，PostgreSQL advisory lock 保证同一时刻只有一个复查事务写状态和通知。授权后即时复查发生在授权事务提交之后；复查或通知失败不会回滚已经提交的授权，但会输出 `permission_review_immediate_failed` 结构化错误，下一次复查继续重试。

## 核准基线

基线包含四类稳定事实：

1. 当前启用的 L1/L2 `resourceKey -> parentResourceKey`，用于发现新增、移除和跨模块转移。
2. 当前已审核的全部用户、岗位和部门显式授权，使用 username、岗位编码和部门编码，不保存易漂移的数据库 ID；业务授权常态应落在岗位或部门，个人直授只能由 root admin 作为例外维护，当前常态基线为零。
3. 如果存在经 root admin 核准的直授例外，保存这些用户的岗位/部门；同时保存持有显式授权的岗位/部门当前任职人员，用于发现“人调走了但直授没撤”和“岗位换人未复核”。
4. 隐式全资源授权管理员岗位和提交/审批职责分离规则。

`npm run permission-review:baseline` 只向 stdout 生成候选 JSON，不直接覆盖核准配置。操作者必须检查 diff、解释变更原因并按租户配置发布流程提交，不能把数据库当前状态自动认定为正确状态。

## 异常分类

- 新增、移除或转移 L1/L2，基线尚未同步。
- 任意显式授权新增、漏撤销或应有授权消失。
- 非 root 操作者尝试维护个人直授会由写入口直接拒绝；基线外个人直授、直授用户调岗，或持有授权的岗位/部门任职人员变化仍进入异常复查。
- 停用用户、Agent、岗位、部门或停用资源仍保留授权。
- action 不存在，或资源不支持该 action。
- 同一有效用户同时具备配置中的提交/填报与审批/复核资格时，只形成流程职责分离提示；这两类权限可以授给同一人，具体单据仍必须由 workflow/service 阻止提交人本人审批或复核。
- 隐式全资源授权管理员岗位与基线不一致。

结果按 fingerprint 去重，状态保存在 `SystemConfig.security.permissionReview.state.v1`。真正的异常首次出现立即强提醒，未解决时按租户配置的 `remindOpenAfterHours` 重复提醒；流程职责分离提示仅首次发送普通通知，不要求确认、不重复追催。恢复后从 open state 移除，未来再现会重新通知。

## 通知与责任人

通知使用 Platform 注册类型 `security.permissionReview.alert`。真正的异常是需要确认的站内强提醒；流程职责分离提示使用同一结构化类型，但覆盖为普通、无需确认的通知。通知发送人是租户配置中的发布运维 Agent，收件人必须是显式、可登录的稳定 username；当前租户同时通知 root 管理员与全资源管理责任人。通知正文列出摘要，完整明细保存在 payload 和服务器结构化日志。

## 维护步骤

1. 先运行 `npm run permission-review:check`，确认当前异常和既有基线。
2. 对新增 L2、模块转移、岗位换人、高风险组织授权或 root 个人直授例外逐项取得业务 owner 与权限责任人确认。
3. 运行 `npm run --silent permission-review:baseline` 生成纯 JSON 候选配置，人工审查 topology、grant、role/assignment 和职责分离 diff。
4. 通过租户配置仓库提交和部署，不直接编辑服务器文件。
5. 部署后再次运行只读复查；非法 action 和错授必须整改。提交/审批资格重合只作为提示，验证对应 workflow/service 的对象级本人处理阻断后即可保留权限。
