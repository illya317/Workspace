# Platform Governance UI

`PlatformGovernanceClient` owns one same-page tab surface:

| Tab | Content | Access |
| --- | --- | --- |
| UI | Core UI declaration registry and capability details | `settings.governance` entry/read |
| 数据关系 | Module-owned PostgreSQL table structure plus the full PK/FK relationship graph | root only |
| SQL 设置 | Live PostgreSQL catalog plus governed runtime-setting and credential operations | root only; writes also use `configure` |
| 模块管理 | Module runtime enable/disable tree and build-time source analysis | root only; writes also use `configure` |
| 运维记录 | Signed SQL operations plus append-only relation-policy revisions, with source/status/search filters and pagination | explicit `settings.governance.audit` |

Tab selection is local client state and does not navigate or synchronize the URL. `UiComponentsShowcase` accepts the shared tabbar so the UI registry remains the original implementation rather than a copied view.

`SQL 设置` calls `/api/settings/governance/sql-settings` and uses the shared master/detail body with an exact desktop ratio of `3:7`. The left selector groups accounts/passwords, network/TLS, query/lock, audit, and backup/recovery settings. The right side begins with one compact environment line instead of summary cards, then renders the selected settings and their management actions directly. The catalog reads only an explicit allowlist from `pg_settings` plus the current connection's safe TLS identity. Settings hidden from the least-privilege runtime role remain explicitly marked as unreadable; the page does not grant `pg_read_all_settings` or silently replace missing evidence with a guessed value. It never returns passwords, connection URLs, HBA contents, file paths, archive commands, or private keys.

Root users with `settings.governance.configure` may enqueue three allowlisted runtime timeout changes and a runtime-password rotation. PATCH requests require an idempotency key, expected-current timeout evidence, an explicit reason, and exact rotation confirmation. They write only a bounded `SystemConfig` operation record; the web process never runs privileged SQL and never receives a generated credential. A separately installed host worker claims one request at a time, rechecks stale values and timeout relationships, applies only predeclared SQL, verifies the observed result, and writes a secret-free result. Password rotation is generated on the host, journaled in a root-only file, updates the database role and mounted secret together, recreates the application, and rolls back or enters `reconciliation_required` on an indeterminate interruption. TLS, HBA, server logging, WAL, listener, and backup changes remain host-operation-only.

Database relations call `/api/settings/governance/database-schema`. Its `表结构` view uses the shared Platform category/direct-item/detail workspace: the left tree is the registered L1/L2 module hierarchy, the top-right grid contains tables directly owned by the selected module, and the lower-right area contains the selected table fields and foreign-key relations. `关系图` retains the full network view behind a toolbar segment. Prisma model families map to canonical module resource keys; an unexpected live table is surfaced under `未归属` instead of being silently classified as Platform.

`关系规则` calls `/api/settings/governance/relation-policies` and uses a module-to-relation master/detail tree. Every registered relation is visible, including modules with no editable relation; unmatched live foreign keys are shown under their database owner or `未归属` as invalid read-only evidence. The right-hand editor deliberately contains only `删除联动` and `业务必填`. A field is editable only when the Relation Catalog explicitly allowlists values and a domain runtime consumes the persisted policy; otherwise the UI states why it is fixed or incomplete instead of presenting a decorative control. `数据库证据`常驻展示且没有折叠入口，其中约束名、端点、列可空性和 `onDelete` 仍全部只读。

`删除联动` writes only `targetDelete`. Registrations sharing one mutation-impact `adapterKey` are saved as one atomic policy group, with a code baseline, effective value, optimistic version, required change reason, reset action, and append-only audit revision. Settings policy mutations and Work consumers acquire the same transaction-scoped advisory lock before CAS or snapshot reads, so a committed domain mutation cannot execute with a concurrently replaced policy. Work mutation-impact includes the snapshot revision in confirmation tokens. Only choices supported by the corresponding delete UI are allowlisted; WorkItem and Project owned-detail groups therefore expose block or automatic owned-child cascade, while WorkPlan may also expose confirmed cascade. Persisted archive, restore, or reference-change fields are cleanup-only legacy evidence: runtime fails closed until root explicitly resets them. Non-empty retired or unregistered policy rows remain visible as stale reset-only entries instead of being silently ignored.

`业务必填` is independent of PostgreSQL nullability. A nullable FK is not inferred to be optional: the relation must declare an explicit business baseline and configurable choices, and its server validator and form must resolve the same persisted value. Switching to required first counts existing null rows and fails closed when any remain. The preflight, config CAS, and revision audit run in one locked transaction; contract create/update/revision-publish paths take the same policy locks and revalidate inside their own transaction. A physical `NOT NULL` relation is fixed required. PostgreSQL FK name, source/target columns, `onDelete`, and nullability are displayed as read-only evidence; policy writes never run DDL or change constraints, permissions, adapters, or endpoints.

Module management calls `/api/settings/governance/modules`; its snapshot is generated during dev/build and the request never scans source code. Both route handlers retain the existing root restriction.

Source analysis derives every file's effective responsibility from source structure and dependency closure, then enforces the default direction `入口 -> 应用 -> 适配 -> 领域 -> 契约` together with `业务 -> Platform -> Core/Data Model`. Cross-business imports, reverse role edges, skipped layers such as input-to-persistence, implementation imports of its own public barrel, and production imports of test/tooling all block snapshot validation. The UI's invalid-direction count comes from the complete backend edge set, so expanding or collapsing grouped columns cannot change it; green relation highlighting is reserved for exact file cycles rather than aggregate two-way role traffic.

The source-governance navigation is the rendered recursive Module contract, not a second UI catalog. It exposes every declared node from L1 to the deepest registered leaf, preserves zero-direct-file aggregation parents, and renders only direct children at each selected level. Parent totals aggregate the complete descendant subtree. Product, shared, data, operations, and tooling children use distinct semantic column sets; leaf detail exposes direct responsibility, dependency targets, and Module-health review evidence.

The Operations Records tab calls the canonical `/api/modules/settings/governance/operations` endpoint. Its DTO declares each provider's provenance and maximum read size, retains a 180-day view window, and fails closed on malformed signed SQL records. The UI never reads deployment receipts, `.cache` files, server directories, or NDJSON. New providers must remain database-backed and add explicit provenance, retention, filtering, and `settings.governance.audit` coverage before joining the aggregate.
